# Installation and release

## Requirements

- Python 3.12+ for the CLI and existing deterministic scripts.
- Blender is optional for existing Godot projects; required only for modeling
  and asset generation. Blender MCP is optional and requires its Blender addon
  server to be running.
- Godot is required for project import/runtime/build checks. The toolkit's
  existing `tools/env.sh` can locate its pinned Linux binary or a `godot` on
  `PATH`; other OS builds should configure `GODOT` explicitly.
- Android export additionally needs matching Godot Android templates, Android
  SDK/build-tools, JDK 17, and a debug or release keystore. AAB distribution also
  needs Godot's Gradle Android template and release signing. See
  [`android-export.md`](android-export.md).
- OpenCode, Kilo, Cursor, and the MCP SDK are optional and only needed for their
  corresponding integration.

## Checkout install

From this checkout:

```sh
./bin/lopodev --version
./bin/lopodev doctor
./bin/lopodev install opencode --project /path/to/workspace --dry-run
./bin/lopodev install opencode --project /path/to/workspace
```

Equivalent targets: `kilo`, `cursor`, and `mcp`. Use
`lopodev uninstall <target> --dry-run` to preview a safe cleanup. Installers report each path
and preserve unrelated existing files; the `mcp` target prints a registration
for you to merge into another client's config.

## Integrations, activation and diagnostics

`lopodev setup` (also run by `install` and `new` unless `--no-integrations` or
`LOPODEV_NO_INTEGRATIONS=1`) installs the pins in `resources/integrations.json`
into `$LOPODEV_DATA` (default `~/.local/share/lopodev`):

- skill packs: downloaded from the pinned commit, SHA-256 checked, extracted
  without links or `..` paths, exposed through stable links in `skills/`;
- Blender MCP: an isolated venv (`uv` when present, else `venv` + `pip`), then
  the upstream `install-addon` plus enabling the addon in Blender's user
  preferences (`--no-blender-addon` skips this; Blender must be found via
  `BLENDER`, `PATH` or `/snap/bin/blender`);
- Godot MCP: an isolated npm prefix; `GODOT_PATH` defaults to the pinned Godot;
- Code Map: an existing `codemap` is kept as-is; otherwise `brew install
  jordancoin/tap/codemap` or `go install`.

Reruns are no-ops (no downloads) and a failure in one component leaves the
others installed and is reported with a recovery hint. Agent configs launch
servers through `lopodev mcp-run <server>`, so they contain no versioned paths.

Activation: OpenCode reads `opencode.json`, agents and skills when a session
starts. LopoDev never kills a running session; restart it yourself, then run
`lopodev doctor --project <workspace>`. Doctor asks OpenCode what a new session
would see (`opencode debug skill`, `opencode mcp list`) and fails on any missing
skill or unconnected server; `--probe` makes one real read-only tool call per
server (`get_godot_version`, `get_structure`, `get_scene_info`). Blender tool
calls report `NOT RUN` until Blender is open with the addon.

`bin/lopodev` is the CLI. `tools/install_lopodev.sh` remains as a deprecated
compatibility wrapper. On Windows, invoke the CLI with
`python tools/lopodev_cli.py` until a native Windows launcher is supplied.

## Homebrew

The formula is `Formula/lopodev.rb` in this repository, generated by
`tools/homebrew_formula.py` (CI fails if it is edited by hand). Tap the
repository by URL:

```sh
brew tap rohan-murmu/lopodev https://github.com/rohan-murmu/lopodev
brew install --HEAD rohan-murmu/lopodev/lopodev   # before the first release
brew install rohan-murmu/lopodev/lopodev          # once a stable formula is committed
```

The wrapper sets `LOPODEV_HOME` to `opt/lopodev/libexec` and the MCP launcher to
`opt/lopodev/bin/lopodev`. Both are stable across versions, so workspaces and
agent configs keep working after `brew upgrade` and `brew cleanup`. User data
(`~/.local/share/lopodev`: knowledge, integrations) and your workspaces are never
touched by upgrade or `brew uninstall lopodev`; remove them yourself if wanted.

Verified locally on Homebrew 7.0.10 (Linux) with a release-style archive in a
temporary tap: `brew install`, `brew test` (CLI, knowledge validation, world
validation, offline `lopodev new`), `brew audit --strict`, an upgrade
0.2.0-dev -> 0.2.1-dev followed by `brew cleanup` with an existing workspace
still resolving, and uninstall leaving user data in place. Installing from the
public GitHub tap has not been exercised until these files are pushed.

### Release procedure

1. Update `VERSION` (semantic version) and commit; run `lopodev verify`.
2. Tag and push `v<VERSION>`. `.github/workflows/release.yml` checks the tag
   matches `VERSION`, runs the tests and path sanitizer, builds
   `lopodev-<VERSION>.tar.gz` with `git archive`, and publishes it with its
   `.sha256` and a stable `lopodev.rb` rendered from that exact archive.
3. Download the published archive and regenerate the formula from it (the
   helper hashes the bytes; it never takes a typed digest):

   ```sh
   python3 tools/homebrew_formula.py --version <VERSION> \
     --archive-file lopodev-<VERSION>.tar.gz --license MIT \
     --output Formula/lopodev.rb --force
   brew style Formula/lopodev.rb
   brew audit --strict --formula Formula/lopodev.rb   # after tapping
   brew install rohan-murmu/lopodev/lopodev && brew test rohan-murmu/lopodev/lopodev
   ```

4. Commit the formula. CI runs `homebrew_formula.py --check Formula/lopodev.rb`,
   which re-renders from the version and checksum in the file and fails on any
   hand edit.

Installed users update with `brew update && brew upgrade lopodev`
(`lopodev update` prints this).
